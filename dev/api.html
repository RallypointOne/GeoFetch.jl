API

Types

All

All()

Selector that keeps everything along a dimension, or every variable, in a Select. Equivalent to not naming that dimension at all; useful for making intent explicit, as in Select(vars=All()).

Between

Between(lo, hi)

Selector for Select that keeps the coordinate values in the closed interval [lo, hi]. Works for anything ordered: numbers, Dates, DateTimes. lo and hi must have the same type, so write Between(0.0, 20.5) rather than Between(0, 20.5).

Pipeline

Pipeline

An ordered chain of stages: one Source, any number of Transforms, and one Sink. Pipelines are built with | and are plain values: building, printing or extending one does no I/O. Pass it to execute to download the data and write the store.

Example

pipeline = OISST(start=Date(2025, 1, 1), stop=Date(2025, 1, 3)) |
    Select(vars=:sst) |
    Store("oisst.zarr")
execute(pipeline)

Rechunk

Rechunk(; dim=n, ...)

Transform that sets the chunk size of the output store along the named dimensions, for example Rechunk(time=30). It changes only how the data is laid out on disk, not what is fetched. Dimensions that are not named keep the source’s native chunk size, and Store(path; chunks=...) takes precedence over Rechunk.

Select

Select(; vars=..., dim=selector, ...)

Transform that narrows a pipeline to part of the source. Each keyword names a dimension of the source (for example lon, lat, time, level), and vars picks variables. Anything not named is kept whole.

A dimension selector is one of

  • Between(lo, hi): values in a closed interval,
  • a range, such as Date(2025, 1, 1):Day(1):Date(2025, 1, 5): values in the range,
  • a vector, such as [850, 500]: exactly those values,
  • All(): everything.

vars takes a Symbol, a vector of Symbols, or All().

On a projected grid (such as HRRR, with dimensions x and y), lon and lat are two-dimensional auxiliary coordinates. They are selected the same way, and keep the smallest x/y rectangle that contains every grid point matching all of them, so some points just outside the requested box are kept as well.

Kept values stay in the source’s order. The selection is applied before anything is downloaded: files, variables and levels that are not selected are never fetched.

Example

Select(vars=[:t2m, :t], level=[850, 500], lon=Between(0, 30), lat=Between(35, 60))

Sink

Sink <: Stage

The last stage of a pipeline: where the data is written. The only sink is Store, a Zarr store on local disk.

Source

Source <: Stage

The first stage of a pipeline: an upstream dataset, described by a schema (dimensions and variables) and a list of fetch units (the pieces it is downloaded in, typically one remote file each).

Sources are normally built by a preset such as OISST, GFS or IFS. A new source type provides schema(src) and units(src) (by default the fields of those names) and a method fetch!(src, unit, schema) returning the unit’s variables as arrays shaped for the selected (narrowed) schema.

Stage

Stage

Abstract supertype of everything that can appear in a Pipeline: a Source, a Transform or a Sink. Stages are combined with |, as in source | transform | sink.

Store

Store(path; chunks=Dict(), zarr_version=3, overwrite=false, attrs=Dict())

Sink that writes a Zarr store to the local directory path. Each dimension becomes a coordinate array of the same name and each variable a data array. Auxiliary coordinates (the two-dimensional lon and lat of a projected grid) are stored as arrays of their own. Date and DateTime coordinates are stored as integers with CF units and calendar attributes.

Keyword arguments

  • chunks: chunk size per dimension, such as Dict(:time => 30). Takes precedence over Rechunk and over the source’s native chunks.
  • zarr_version: 2 or 3.
  • overwrite: replace an existing store at path. When false, an existing store makes execute throw.
  • attrs: extra attributes for the root group, merged over the source’s.

Transform

Transform <: Stage

A middle stage of a pipeline. Select narrows dimensions and variables; Rechunk sets the chunk shape of the output.

Functions

AIFS

AIFS(; start, stop, cycles=0:6:18, steps=[0], base=...)

ECMWF Artificial Intelligence Forecasting System (AIFS Single) deterministic forecasts on a regular global 0.25° lat/lon grid, read from the GRIB2 files of the ECMWF open data (CC-BY-4.0). Works like IFS, with which it shares the file layout, the dimensions and the variable naming.

Keyword arguments

  • start, stop: first and last cycle Date (inclusive). The file layout used here starts on 2025-03-01.
  • cycles: initialization hours (UTC) to use on each date, any of 0, 6, 12, 18.
  • steps: forecast lead times in hours, multiples of 6 up to 360.
  • base: root location of the YYYYMMDD/HHz/aifs-single/ tree, see IFS.

Dimensions

lon (from -180 eastwards), lat (north first), level (hPa, 14 levels from 1000 up to 10), step and time, as for IFS. One file, hence one fetch unit, exists per (time, step).

Variables

On (lon, lat, step, time): t2m, d2m, u10, v10, u100, v100, skt, msl, sp, tcc, lcc, mcc, hcc, tcw, tp, cp, sf, rowe, fscov, ssrd, strd, lsm, zsfc, sdor, slor, and the soil layers sot1, sot2, vsw1 and vsw2.

On (lon, lat, level, step, time): t, u, v, w, z, gh, q.

All are stored as Float32. Some units differ from IFS: tp, cp and sf are in kg m⁻² (accumulated since forecast start) and cloud cover is in %.

!!! warning Without a Select(vars=...) every variable above is fetched on every level: about 125 sequential range requests per (cycle, step). Select the variables, levels and region you need.

A message that a file does not contain is stored as NaN rather than raising an error, for example lsm, zsfc, sdor and slor at any step but 0, or variables and levels that were added to the open data after the selected dates.

Example

using GeoFetch, Dates

pipeline = AIFS(start=Date(2026, 11, 14), stop=Date(2026, 11, 14), cycles=[0], steps=0:6:24) |
    Select(vars=[:t2m, :tp], lon=Between(0, 30), lat=Between(30, 60)) |
    Store("aifs.zarr")
execute(pipeline)

ERA5(; start, stop, variables, levels=nothing)

ECMWF ERA5 reanalysis from the Copernicus Climate Data Store. Not implemented yet: calling it throws an error.

GFS

GFS(; start, stop, cycles=0:6:18, steps=[0], resolution="0p25", base=...)

NOAA Global Forecast System (GFS) forecasts on a regular global lat/lon grid, read from the pgrb2 GRIB2 files of the public AWS bucket noaa-gfs-bdp-pds. Returns a GRIBRangeSource: only the GRIB messages of the selected variables and levels are downloaded, located through the .idx sidecar of each file and fetched with HTTP byte-range requests.

Keyword arguments

  • start, stop: first and last cycle Date (inclusive). The bucket layout used here starts on 2021-03-23.
  • cycles: initialization hours (UTC) to use on each date, any of 0, 6, 12, 18.
  • steps: forecast lead times in hours, within 0:384. At "0p25" every hour up to 120 is available, beyond that (and at the other resolutions) only multiples of 3.
  • resolution: "0p25", "0p50" or "1p00" (grid spacing in degrees).
  • base: root location of the gfs.YYYYMMDD/HH/atmos/ tree. Defaults to the AWS bucket; pass the URL of a mirror or a local directory with the same layout (GRIB files plus their .idx sidecars) to read from there instead.

Dimensions

  • lon: degrees east, from 0 eastwards.
  • lat: degrees north, from 90 down to -90 (north first).
  • level: isobaric level in hPa, from 1000 up to 1 (33 levels).
  • step: forecast lead time in hours.
  • time: forecast initialization time (the cycle), one per date and cycle.

One file, hence one fetch unit, exists per (time, step).

Variables

On (lon, lat, step, time): t2m, d2m, rh2m, u10, v10, gust, prmsl, sp, pwat, cape, tcc, apcp, orog, lsm.

On (lon, lat, level, step, time): t, u, v, w, z, rh, q.

All are stored as Float32. apcp is the precipitation accumulated since forecast start.

!!! warning Without a Select(vars=...) every variable above is fetched on every level: about 245 sequential range requests and on the order of 1 GB in memory per (cycle, step) at "0p25". Select the variables, levels and region you need.

A message that a file does not contain is stored as NaN rather than raising an error, for example apcp at step 0 or a level that a variable lacks.

Example

using GeoFetch, Dates

pipeline = GFS(start=Date(2026, 11, 8), stop=Date(2026, 11, 8), cycles=[0], steps=0:6:24) |
    Select(vars=[:t2m, :t], level=[850, 500], lon=Between(0, 30), lat=Between(30, 60)) |
    Store("gfs.zarr")
execute(pipeline)

HRRR

HRRR(; start, stop, cycles=0:23, steps=[0], base=...)

NOAA High-Resolution Rapid Refresh (HRRR) forecasts over the contiguous United States on a 3 km grid, read from the GRIB2 files of the public AWS bucket noaa-hrrr-bdp-pds. Returns a GRIBRangeSource: only the GRIB messages of the selected variables and levels are downloaded, located through the .idx sidecar of each file and fetched with HTTP byte-range requests.

Keyword arguments

  • start, stop: first and last cycle Date (inclusive). The bucket starts on 2014-07-30.
  • cycles: initialization hours (UTC) to use on each date, within 0:23.
  • steps: forecast lead times in hours: up to 18, and for the 0, 6, 12 and 18 UTC cycles up to 48. Older runs are shorter (36 before December 2020, 18 before July 2018).
  • base: root location of the hrrr.YYYYMMDD/conus/ tree. Defaults to the AWS bucket; pass the URL of a mirror or a local directory with the same layout (GRIB files plus their .idx sidecars) to read from there instead.

Dimensions

The grid is regular in a Lambert conformal projection, not in longitude and latitude, so the horizontal dimensions are the projected coordinates.

  • x: projected easting in m, 1799 points from west to east.
  • y: projected northing in m, 1059 points from south to north.
  • level: isobaric level in hPa, from 1000 up to 50 in steps of 25 (39 levels).
  • step: forecast lead time in hours.
  • time: forecast initialization time (the cycle), one per date and cycle.

lon (degrees east, about -134 to -61) and lat (degrees north, about 21 to

  1. are two-dimensional auxiliary coordinates on (x, y), stored next to the

variables. A Select on lon and lat keeps the smallest x/y rectangle that contains the matching grid points. The projection is recorded as a PROJ string in the crs attribute of the store.

Two files, hence two fetch units, exist per (time, step): wrfsfc with the single-level variables and wrfprs with the pressure-level variables.

Variables

On (x, y, step, time): t2m, d2m, rh2m, q2m, u10, v10, u80, v80, gust, prmsl, sp, skt, pwat, cape, cin, tcc, lcc, mcc, hcc, vis, refc, hpbl, prate, apcp, asnow, snod, weasd, dswrf, dlwrf, shtfl, lhtfl, smoke, colmd, orog, lsm.

On (x, y, level, step, time): t, u, v, w, z, rh, q.

All are stored as Float32. apcp and asnow are accumulated since forecast start.

!!! warning Wind components (u10, v10, u80, v80, u, v) are relative to the grid: u is along x and v along y, which away from the central meridian (97.5° W) is not due east and north.

!!! warning Without a Select(vars=...) every variable above is fetched on every level: about 310 sequential range requests and several GB in memory per (cycle, step). Select the variables, levels and region you need.

A message that a file does not contain is stored as NaN rather than raising an error, for example variables that were added in later versions of the model (such as smoke and colmd, added in December 2020).

Example

using GeoFetch, Dates

pipeline = HRRR(start=Date(2026, 11, 14), stop=Date(2026, 11, 14), cycles=[0], steps=0:3) |
    Select(vars=[:t2m, :t], level=[850, 500], lon=Between(-110, -100), lat=Between(35, 42)) |
    Store("hrrr.zarr")
execute(pipeline)

IFS

IFS(; start, stop, cycles=0:6:18, steps=[0], resolution="0p25", base=...)

ECMWF Integrated Forecasting System (IFS) high-resolution deterministic forecasts on a regular global lat/lon grid, read from the GRIB2 files of the ECMWF open data (CC-BY-4.0). Returns a GRIBRangeSource: only the GRIB messages of the selected variables and levels are downloaded, located through the .index sidecar of each file and fetched with HTTP byte-range requests.

Keyword arguments

  • start, stop: first and last cycle Date (inclusive). The file layout used here starts on 2024-03-01.
  • cycles: initialization hours (UTC) to use on each date, any of 0, 6, 12, 18.
  • steps: forecast lead times in hours: multiples of 3 up to 144, and for the 0 and 12 UTC cycles also multiples of 6 up to 360. Older runs are shorter: the 6 and 18 UTC cycles end at 90 before 2026-05-12, the 0 and 12 UTC cycles at 240 before November 2024.
  • resolution: "0p25", or "0p1" (0.1°, from 2026-10-21).
  • base: root location of the YYYYMMDD/HHz/ifs/ tree. Defaults to the Google Cloud mirror; pass the URL of another mirror (the AWS bucket https://ecmwf-forecasts.s3.eu-central-1.amazonaws.com, or https://data.ecmwf.int/forecasts, which keeps about the last 4 days) or a local directory with the same layout (GRIB files plus their .index sidecars) to read from there instead.

Dimensions

  • lon: degrees east, from -180 eastwards (unlike GFS, which starts at 0).
  • lat: degrees north, from 90 down to -90 (north first).
  • level: isobaric level in hPa, from 1000 up to 10 (14 levels).
  • step: forecast lead time in hours.
  • time: forecast initialization time (the cycle), one per date and cycle.

One file, hence one fetch unit, exists per (time, step); at "0p1" there are two, one with the pressure-level variables and one with all the others.

Variables

On (lon, lat, step, time): t2m, d2m, u10, v10, u100, v100, fg10, mx2t3, mn2t3, skt, msl, sp, tcc, lcc, mcc, hcc, tcw, tcwv, tclw, tciw, tcrw, mucape, tp, cp, sf, ro, tprate, ptype, ssrd, ssr, strd, str, ttr, ewss, nsss, sd, rsn, asn, sithick, zos, sve, svn, lsm, zsfc, sdor, slor, and the soil layers sot1 to sot4 and vsw1 to vsw4.

On (lon, lat, level, step, time): t, u, v, w, z, gh, q, r, d, vo.

Names are the ECMWF short names, except that a leading number moves to the end (2t is t2m, 10u is u10, 10fg is fg10), the surface geopotential z is zsfc, and the soil parameters sot and vsw carry their layer number. All are stored as Float32. tp, cp, sf, ro and the radiation and stress fields are accumulated since forecast start; tp is in metres. z is the geopotential in m² s⁻² and gh the geopotential height.

!!! warning Without a Select(vars=...) every variable above is fetched on every level: about 190 sequential range requests and on the order of 1 GB in memory per (cycle, step) at "0p25", and about six times that at "0p1". Select the variables, levels and region you need.

A message that a file does not contain is stored as NaN rather than raising an error. That applies to zsfc, sdor and slor at any step but 0, to mx2t3 and mn2t3 beyond step 144, and to the many variables and levels that were added to the open data over time (in March 2024 it had 11 single-level variables and 9 levels). Ocean fields are NaN over land.

Example

using GeoFetch, Dates

pipeline = IFS(start=Date(2026, 11, 14), stop=Date(2026, 11, 14), cycles=[0], steps=0:6:24) |
    Select(vars=[:t2m, :t], level=[850, 500], lon=Between(0, 30), lat=Between(30, 60)) |
    Store("ifs.zarr")
execute(pipeline)

OISST

OISST(; start, stop)

NOAA Optimum Interpolation Sea Surface Temperature (OISST) v2.1, AVHRR-only: daily fields on a 0.25° global grid, read from NCEI over HTTPS. Returns an HTTPFileSource with one NetCDF file (about 1.6 MB) per day from start to stop (Dates, inclusive).

Dimensions

  • lon: degrees east, 0.125 to 359.875.
  • lat: degrees north, -89.875 to 89.875.
  • zlev: a single level at 0 m.
  • time: one Date per day.

Variables

All on (lon, lat, zlev, time) as Float32, with NaN where there is no data (such as sst over land): sst (sea surface temperature, °C), anom (anomaly from the climatological mean, °C), err (estimated error standard deviation, °C), ice (sea-ice concentration).

Example

using GeoFetch, Dates

pipeline = OISST(start=Date(2025, 1, 1), stop=Date(2025, 1, 3)) |
    Select(vars=:sst, lon=Between(280, 350), lat=Between(20, 60)) |
    Store("oisst.zarr")
execute(pipeline)

execute

execute(pipeline)

Run a Pipeline: apply its Selects, create the Zarr store described by its Store, then fetch each remaining unit from the source and write it into place. This is the only operation that downloads data or touches the disk. Returns the root group of the new store.

Throws if the store already exists and was not created with overwrite=true.
